DEAD SIGNAL — Google Play 사전 테스트·Android 화면 확보 경로
조사일: 2026-10-16 / 로컬 자료 재검증: 2026-10-16T02:40:50Z 전후
범위: Google 공식 문서 현재 조회, 현재 출시 자료 읽기 전용 검사. 계정·브라우저 UI·게임·바이너리·사용자 저장 데이터 변경 없음.

현재 결론
첫 서명 AAB를 내부 테스트에 업로드하면 자동 pre-launch report의 실행 대상이 될 수 있다. 프로덕션 승인이나 사람 테스터 옵트인이 끝날 때까지 기다려야만 랩 테스트가 가능한 구조로 공식 문서가 설명하지는 않는다. 다만 업로드마다 테스트·결과·스크린샷이 반드시 생성되는 것은 아니다. 업로드 성공, 랩 실행, 실제 전투 검수, 스토어 스크린샷 확보는 서로 다른 완료 상태다.
현재 실제 Android 화면 증거는 0장이고, 앱 설치·실행·터치 플레이도 검증되지 않았다. 브라우저 화면이나 Play Console 화면을 Android 게임 화면으로 바꾸어 설명하지 않는다.

1. 자동 pre-launch report의 공식 조건
Google Play는 AAB/APK 업로드 또는 프로덕션 릴리스 저장을 트리거로 설명한다. 기기 랩 용량이 허용해야 실행되며, 테스트 가능한 메인 실행 Activity와 설치·탐색 가능한 앱이 필요하다. 시작 후에는 기기에서 앱을 실행해 몇 분 동안 기본 입력을 탐색한다.
공식 안내의 통상 결과 시간은 업로드 후 약 1시간이나 수시간 걸릴 수 있다. 이것은 SLA가 아니다. ‘Testing in progress’, ‘Test failed’ 및 실제 보고서 존재를 확인해야 한다.
설정에서 Robo script, game loop, deep link, 언어를 조정할 수 있다. 게임은 game loop로 유용한 경로를 유도할 수 있으나 앱 내 구현이 필요하다. 처음 업로드의 자동 테스트가 끝난 뒤에 언어 설정이 반영되는 제한도 있다.
출처 A: https://support.google.com/googleplay/android-developer/answer/9842757?hl=en
확인한 내용: 자동 생성 및 랩 용량, 메인 Activity, 설정, 결과 조회, 통상 대기 시간.

적용 판단(위 문서에서의 추론)
내부 테스트 업로드는 기존 AAB를 유지하면서 자동 랩 결과를 먼저 확인할 수 있는 경로다. 이 문서는 사람 테스터 목록이나 프로덕션 심사 완료를 자동 랩 실행의 선행조건으로 열거하지 않는다. 따라서 둘을 자동 테스트의 필수 조건으로 임의로 추가하지 않는다. 단, 현재 계정·앱에 실제로 작업이 배정되는지는 Console에 올라온 결과만이 증거다. ‘업로드만 하면 확실히 시작된다’고 보장하지 않는다.

2. 사람의 내부 테스트 설치는 별도 절차
앱 설정이 완전하지 않아도 유효한 AAB로 내부 테스트를 시작할 수 있다. 내부 테스트는 최대 100명의 Google/Workspace 계정 테스터를 대상으로 하며, 일반 정책·보안 심사가 적용되지 않을 수 있다. 첫 정식 검토 전에는 임시 이름·등록 정보가 보일 수 있다. 이 경로는 프로덕션 공개 승인을 선행조건으로 하지 않는다.
실제 사람에게는 테스트 릴리스 배포, 테스터 목록 선택과 해당 사용자의 옵트인이 필요하다. Draft/Pending publication 상태에는 옵트인 링크가 표시되지 않는다. 비공개 테스트는 검색으로 찾아 설치하는 방식이 아니므로 링크를 전달한다. 첫 링크나 변경 사항 전파에 수시간 걸릴 수 있어 ‘수분 내’ 안내만으로 설치 성공을 단정하지 않는다.
출처 B: https://support.google.com/googleplay/android-developer/answer/9845334?hl=en-GB
자동 랩 기기는 이 사람 테스터 목록과 구분한다. 본 조사에서는 누구도 초대하거나 이메일을 임의로 테스터 목록에 넣지 않았다.

3. 결과에서 실제 Android 이미지·영상 확인
Console 경로: Test and release → Testing → Pre-launch report → Details.
Screenshots 탭에서는 기기별/화면 묶음별 이미지를 확인하고, 모델·Android 버전·화면 해상도·언어 등 메타데이터를 대조한다. Stability/Performance의 기기 상세에서는 가능한 경우 영상·스크린샷·로그를 확인한다. 자료의 제공 여부는 테스트마다 다를 수 있다. demo/game loop 실행에는 Screenshots 탭 데이터가 나오지 않는다는 제한이 명시되어 있다.
출처 C: https://support.google.com/googleplay/android-developer/answer/9844487?hl=en
실무 제안: 보고서가 생기면 해당 versionCode, 실행된 기기, 실제 게임까지 진입했는지, 이미지 해상도와 오류를 기록하고 원본 자료를 보존한다. 다운로드 버튼이 있으면 원본을 사용한다. 이 조사에서는 Console의 다운로드 UI나 실제 생성 파일을 확인하지 않았다. 보고서 페이지를 캡처한 이미지 자체를 게임 원본 스크린샷으로 쓰지 않는다.

4. DEAD SIGNAL의 자동 탐색 가능성과 한계
확인된 사실: 현재 AndroidManifest.xml에는 MAIN/LAUNCHER Activity가 있다. 게임은 Capacitor WebView 안의 HTML 메뉴와 Canvas 전투로 동작한다. 로그인, 광고, 실제 IAP, 서버 인증, Play 라이선스 검사는 현재 버전에 없다. 별도 테스트 계정을 만들 이유가 없다. 현재 native entry·Manifest·app.js에는 Firebase game loop 의도/시나리오 처리 연결을 찾지 못했다.
Robo 공식 문서는 Android UI hierarchy를 읽을 수 있는 위젯을 탐색하며, 지원되지 않는 화면에서는 반무작위 탭으로 대체한다고 설명한다. 게임용 자동 시나리오는 별도 game loop 경로다.
출처 D: https://firebase.google.com/docs/test-lab/android/robo-ux-test
적용 판단: 초기 설치·실행 오류나 메뉴 화면은 자동 랩에서 확인할 가능성이 있다. 그러나 이 앱의 HTML 메뉴가 실제로 어느 수준까지 노출되는지, Canvas에서 이동·조준·회피를 정상적으로 수행하는지는 실행 전 알 수 없다. 자동 탐색이 메뉴에만 머물면 전투·저장·오프라인·복귀 검수를 통과한 것으로 해석하지 않는다. 자동 사격이 있어도 출격 버튼 진입·이동·이벤트 선택까지 보장되는 것은 아니다.

5. 지금 선택할 수 있는 경로
A. 기존 AAB로 Play 자동 pre-launch 확인 — 우선 추천.
현재 서명 AAB를 내부 테스트 업로드에 사용한다. 업로드 후 versionCode 1의 보고서가 실제 생성되는지 확인한다. 프로덕션 공개 없이 랩 결과 확보를 시도할 수 있으며 코드 수정은 필요 없다. 생성되더라도 Canvas 전투와 저장 복귀는 별도 검수한다.
B. 내부 테스트를 승인된 사람의 Android 기기에 배포.
실제로 설치 가능한 테스터 계정과 기기가 있을 때 배포·옵트인 후 플레이 검수와 기기 원본 캡처를 한다. 현재 사용할 계정·폰을 이 조사에서 확인하지 않았다. Android Play 배포 앱의 서명은 로컬 upload-key QA APK와 다를 수 있으므로, Play에서 전달된 앱을 검사한 것인지 기록한다.
C. 별도 Firebase Test Lab Robo 실행 — 계정·결제 조건 확인 후의 대안.
공식 Firebase Console 절차는 APK 업로드, 기기/API/방향/언어 선택, 테스트 시작과 결과 열람이다. 현재 QA APK를 파일 변경 없이 활용할 가능성이 있으나, 이 조사에서는 프로젝트 생성·API 활성화·업로드·실행을 하지 않았다.
출처 E: https://firebase.google.com/docs/test-lab/android/firebase-console
D. 향후 game loop / instrumented test 추가 — 현재 동결판 외 작업.
게임에 시나리오 진입·플레이·종료 처리를 구현하는 별도 개발 작업이다. 현재 바이너리에서 체크박스만 켜서 사용할 수 없다. 실제 기능 추가 후 새 versionCode로 빌드·서명·재검수가 필요하다. 테스트용 시나리오만 통과했다고 사람의 터치 품질이나 출시판 전체가 검증되는 것도 아니다.
출처 F: https://firebase.google.com/docs/test-lab/android/game-loop

출처 E: https://firebase.google.com/docs/test-lab/android/firebase-console
출처 G: https://firebase.google.com/docs/test-lab/usage-quotas-pricing
현재 목적에는 Play의 자동 pre-launch 경로를 먼저 확인하는 것이 별도 프로젝트/결제 구성을 늘리지 않는 선택이다. 테스트의 실제 생성은 여전히 보장하지 않는다.

7. 버전·재시도 구분
현재 제출 후보는 versionName 1.0.0 / versionCode 1이다. 로컬 원본 해시를 유지한다. 첫 업로드에 이미 사용된 versionCode인지 여부는 Console에서 판단한다.
새 바이너리의 후속 versionCode는 이전보다 높아야 하며, 이미 사용한 버전을 새 파일로 중복 업로드하는 계획은 세우지 않는다. versionName 문자열과 versionCode 정수를 혼동하지 않는다. 기존 번들을 다른 트랙에 재사용/승격하는 것과 새 artifact 업로드는 별개다.
출처 H: https://developer.android.com/studio/publish/versioning
보고서가 늦거나 없다는 이유만으로 즉시 반복 업로드·버전 증가·게임 수정을 하지 않는다. 현재 보고서 상태와 해당 artifact를 먼저 확인한다. 새 테스트 시나리오를 구현할 때만 그 변경에 맞는 새 빌드를 만든다.

8. 스토어 스크린샷 충족 조건
일반 게시 최소는 스크린샷 2장이다. JPEG 또는 알파 없는 24bit PNG, 각 변 320~3840px, 긴 변이 짧은 변의 2배를 넘지 않아야 한다. 게임 추천용 16:9 1920×1080 이상 3장 또는 9:16 1080×1920 이상 3장은 일반 게시 최소와 별도다. 실제 게임 경험을 보여야 한다.
출처 I: https://support.google.com/googleplay/android-developer/answer/9866151?hl=en
적용 판단: pre-launch 이미지도 실제 Android 실행 결과라면 출처·버전·기기를 확인한 뒤 소재 후보로 검토할 수 있다. 자동으로 등록 규격·내용·권리 요건을 모두 통과하는 것은 아니다. 원본이 흐리거나 잘못된 비율, 메뉴뿐인 반복 이미지, 테스트 주석/오류가 섞인 화면이면 추가 원본 캡처가 필요하다. 브라우저 화면 확대·기기 테두리 합성·무드보드 생성으로 실제 Android 증거를 대체하지 않는다.

상태 자료의 시점
RELEASE-STATE.json의 2026-10-16T02:39:38Z 스냅샷은 Console 앱 생성 true, 업로드/심사 제출/공개 false다. root가 계정에서 진행 중인 이후 변경을 이 보고서가 실시간으로 확인하는 것은 아니다.
ANDROID-NATIVE-LAUNCH.json의 실제 결과는 전용 AVD가 두 번의 제한된 부팅 시도 후에도 adb offline, 최종 APK 설치·실행·화면·터치 미검증이다. native UI 연결이 안 되는 Qt 앱을 우회 조작하거나 adb 화면 캡처를 수행하지 않았다. 물리 기기 및 16KB 런타임도 미검증이다.
ANDROID-READINESS.txt와 초기 PRIVACY-READINESS.txt는 서명/공개 URL 준비 이전의 이력을 포함한다. 최종 상태는 최신 서명 보고서·PUBLIC-PAGES·RELEASE-STATE와 구분해 읽어야 한다. 기존 보고서 원본을 덮어쓰지 않았다.

출시 전에 확보할 실제 증거 제안
같은 versionCode의 Android 설치·첫 오프라인 실행, 출격 자산 로드, 터치 이동/오토·수동 사격/회피, 전투와 보스 도감, 앱 배경 전환 후 사용자 재개, 저장·종료·이어하기를 확인한다. 기기/API/WebView/방향과 오류·화면 출처를 기록한다. pre-launch가 이 경로를 실제로 수행하지 않았다면 ‘문제 없음’ 요약을 그 검수의 통과로 확대하지 않는다.
신규 스크린샷은 적어도 실제 전투와 게임 UI의 서로 다른 두 장면을 확보한다. 메뉴에만 머문 자동 랩 결과나 업로드 성공은 그 완료 기준에 미달한다. 공개/프로덕션 심사와는 별개로 이 미검증 상태를 정직하게 남긴다.

이번 작업으로 새로 쓴 파일은 PRELAUNCH-QA-OPTIONS.txt 하나다. 게임·동결 원본·바이너리·키·계정·브라우저 UI·8806 사용자 프로필은 변경하지 않았다. 웹 조사에서 보인 Google 커뮤니티 답변이나 비공식 자료는 정책 근거로 사용하지 않았다.
